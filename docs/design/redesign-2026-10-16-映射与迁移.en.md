## 2. State model field characterization (business state / display fields / local preferences / metadata)

### 2.1 `WidgetState` (`src/Beacon.Core/Models/WidgetState.cs:4-21`)

| Field | Characterization | Notes |
|---|---|---|
| `WidgetId` `WidgetType` `ConnectionId` | Identifier | Stable keys, not state |
| `Severity` `Lifecycle` | **Business state** | Normalized projection of external-system facts |
| `Progress` | **Business state** | 0..1 normalized progress |
| `Payload` | **Business data** | Feeds Action template variables (run_id etc.) |
| `Summary` | **Display field** | Already-localized copy mixed into the business state object (the split point called out in the design draft's §Implementation Suggestions) |
| `DetailUrl` | Business metadata | External detail link, consumed by the Open action |
| `FetchedAt` | Metadata | Freshness; **participates in content equality** (`:36`, counter-evidence in verification table B09) |
| `IsStale` `ConnectionHealthy` | **Derived state** | Inferred from failure / offline, not external facts |

### 2.2 Config fields (`AppConfig.cs` / `WidgetConfig.cs`)

| Category | Fields |
|---|---|
| **Local preferences (Preference)** | `Theme` `UiOpacity` `Appearance.*` (SeverityColors / Motion.Mode / Motion.Intensity / ProgressStyle) `Language` `EdgeCollapseEnabled` `NumericFloatingEnabled` `PinDisplayMode` `ShowCapsule` `SettingsSidebarWidth` `SettingsWindowWidth/Height`; `WidgetConfig.Pinned` `PinLayout` `ColorOverride` |
| Global settings (user intent) | `Hotkey` `LaunchOnStartup` `PollIntervalSeconds` `NotificationRules` |
| Business config | `WidgetConfig.Config` (Provider parameters), all of `ConnectionConfig` |
| Scheduling config | `WidgetConfig.RefreshTier` `RefreshIntervalSeconds` |

**Conclusion**: `Summary` is the only display field inside the business state object; local preferences are already stored in separate files from business config (`config.json` vs `connections.json`/`widgets.json`), so the current isolation is good. Phase 1 only needs to sort out the conventions for `Summary` and the derived fields; the config file structure needs no change.

## 4. Gap and migration plan (by phase)

### Phase 1 Reactive state and data flow

1. Introduce `IStateStore` (in-process implementation): snapshot reads + subscription + content-level change detection. After a successful refresh `WidgetHost` writes into the Store instead, and the Store publishes `WidgetStateChanged` when it detects a change — **the publish point moves from WidgetHost to the Store**; the event contract is unchanged and the UI notices nothing.
2. Change detection rule: remove `FetchedAt` from `WidgetState` content equality (or add `ContentVersion`) so that 「仅刷新时间变化」 (a refresh-time-only change) no longer triggers downstream.
3. Selector consolidation: `QuotaWindows` / `WidgetValueHint` / `QuickPanelSections` / `QuickPanelFilter` are relocated into the Selector layer; signatures unchanged, only the namespace and documentation positioning move.
4. **Regression surface**: after dedup the UI no longer rebuilds every tick — scenarios S (event stream), O (panel counts), Q (capsule counts) must all stay green; F5 (offline degradation produces exactly 1 notification) depends on stale events not being swallowed by dedup, so unit tests come first.
5. Rollback: the Store is introduced as a bypass (revertible as a whole in one commit) and is not merged into the WidgetHost rewrite.

### Phase 2 Design system and base component library

1. Tokenization: `UiPalette` / `ThemeColors` / `MotionEngine` / `DpiLayoutMath` are consolidated into a token layer; **color values must not change** (the G-series CI pixel assertions pin the current color values; changing a value turns them red).
2. The first batch of components is reverse-engineered from `MakeStateRow`: Metric, Status Indicator, Progress, Key-Value, Status Card, List, Action Button, Link, Stack, Grid, Section, Conditional, Empty, Loading, Error, Offline.
3. The visual example page becomes its own window (debug builds only), not part of the product window set.

### Phase 3 Component composition and data binding

1. `Component Descriptor`: add display declarations on top of `WidgetTypeDescriptor` (component type + bindings + density), **without overturning the existing 23 type keys**.
2. `WidgetConfig` gains incremental optional fields (`ConfigVersion` increments, old files stay readable) — the compatibility plan is in §5.
3. Selector-to-component-property binding + multi-source composition (the current single-`ConnectionId` nature of `WidgetState` is not broken; composition happens at the component layer aggregating multiple WidgetIds).

### Phase 4 HTML small screens

**Precondition decision**: the boundary ruling against `docs/master-plan.md:769` 「不引入 WebView 或其他 UI 框架来重复实现桌面外壳」 — does HTML enter only the 「数据显示小屏幕」 (data-display small screens) and not the 「外壳」 (shell), or does everything stay native? No work starts before the ruling.

### Phase 5 / 6

Component catalog expansion and full regression; the 71-item on-machine checklist (`docs/acceptance-checklist.md`) remains the acceptance base, re-run item by item in Phase 6.

## 5. Compatibility plan (proposal, pending decision)

1. The six JSON file names and existing field semantics are **entirely unchanged** (continuing the implemented convention recorded in verification table G02).
2. The new component model enters as incremental optional fields on `WidgetConfig`; `ConfigVersion` increments but old versions stay readable; no migration, no renaming.
3. The existing 23 type keys, 7 Action Type strings, and all window layers are preserved; componentization only replaces the rendering segment and the state entry point, leaving Providers and executors untouched.
4. On-machine acceptance capability is retained: the 71-item on-machine checklist and the CI visual-evidence scenarios remain in force; the phase counts as complete only after the full Phase 6 regression.
